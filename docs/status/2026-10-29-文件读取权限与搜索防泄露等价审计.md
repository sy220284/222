# 2026-10-29 文件读取权限与搜索调用链源码级等价审计

## 原始源码证据

以用户提供的 `claude-code-2.1.88-main(1).zip` 直接读取并对照：

1. `src/utils/permissions/filesystem.ts::checkReadPermissionForTool`：读取前先检查显式 read deny，再检查 read ask；核对请求路径与符号链接解析目标，最后才允许工作区内默认读取。
2. `src/utils/permissions/filesystem.ts::matchingRuleForInput`：权限路径使用工作区相对模式，`/**` 后缀在送入 `ignore` 匹配前会去掉，因此 `secrets/**` 同时匹配 `secrets` 目录自身及子项。
3. `src/tools/FileReadTool/FileReadTool.ts::checkPermissions`：文件读取前调用上述读取权限引擎。
4. `src/tools/GlobTool/GlobTool.ts::checkPermissions` 与 `src/tools/GrepTool/GrepTool.ts::checkPermissions`：**检查的是搜索根目录**（`getPath(input)`），并非逐一对每个命中的文件重新审批。与单文件读取工具存在有意的语义区别。
5. `src/utils/permissions/permissions.ts::toolMatchesRule`、`src/utils/permissions/permissionRuleParser.ts`、`src/utils/permissions/shellRuleMatching.ts`：规则名称、内容解析和 deny/ask/allow 的优先关系。

## 已实际修复

原 Rust `src/tools.rs::read_file` 只检查工作区边界，完全未执行显式 `Read` 权限规则；`permission_rules::canonical_tool` 也未关联 `read_file` 与 `Read`。这会使用户明确禁止的工作区文件被模型直接读取。

现已在 `src/permission_rules.rs` 实现文件路径 glob 匹配、请求路径与符号链接真实目标联合检查、`/**` 目录自身匹配，以及 deny > ask > allow；`src/tools.rs` 在打开文件前执行该检查，读权限不因 ReadOnly/Plan 模式而被无条件拒绝。明确 ask 在无交互环境拒绝，交互环境要求确认。

`Glob`/`Grep` 现在按原版在搜索**根目录**调用同一读取权限检查。此前尝试对每个搜索结果额外过滤（提交 `112315ee`），重新阅读原版后确认会改变用户能搜索到的结果，已在 `e62eb4fc`、`ba4524c7` 撤回，并增加根目录审批测试。自定义 `search_text`、`list_files` 仍按现有 Rust 自定义工具语义逐文件过滤；本地及已启用插件的技能加载和目录列举也遵守显式读取限制。
